# 재고 동시성 제어 방식 비교 — 실험 기록

재고 100개인 인기 상품 하나에 결제 확정 300건이 동시에 몰리는 상황을 PostgreSQL에서 재현하고, 재고 차감 방식 5가지를 같은 측정 코드로 비교한 기록입니다. 처음 질문은 "어떤 락이 빠른가"였지만, 측정해 보니 **정확한 방식끼리의 차이는 작았고(9%) 진짜 비용은 품절될 요청까지 DB 한 행 앞에 줄을 세우는 구조**에서 나왔습니다.

## 요약

| 방식 | 정합성 | 전체 시간 | 성공 p50 / max | 품절 p50 | 비고 |
|---|---|---|---|---|---|
| 락 없음 (재현용) | ❌ **초과 판매 200** | 1,779ms | – | – | 300건 성공, 재고는 3개만 감소 (Lost Update) |
| 비관적 락 | ✅ | 2,161ms | 573 / 958ms | 2,137ms | 품절 요청도 락을 하나씩 잡음 |
| 원자적 UPDATE (기존) | ✅ | 1,968ms | 596 / 989ms | 1,926ms | 재고 0 이후에는 락 없이 실패 |
| 낙관적 락 (`@Version` + 재시도) | ✅ | 3,042ms | 1,285 / 2,155ms | 3,024ms | 충돌 1,291회 (성공 1건당 약 13회) |
| **Redis 문지기 + 원자적 UPDATE** | ✅ Redis = DB = 0 | **1,233ms** | 699 / 1,229ms | **1,006ms** | 품절 요청이 DB 락 대기열에 서지 않음 |

**결론**
1. **락 방식만 바꿔서는 거의 차이가 없습니다.** 비관적 락과 원자적 UPDATE 모두 한 행의 락을 건당 약 10ms씩 차례로 넘겨받습니다. 원자적 UPDATE도 행 락을 잡으며, 차이는 "조회 왕복 없이 짧게 잡는다"는 것뿐입니다.
2. **낙관적 락은 충돌이 몰리는 곳에 맞지 않습니다.** 충돌할 때마다 결제 확정 트랜잭션 전체를 다시 실행해 1.5배 느렸습니다.
3. **품절 요청을 DB 앞에서 걸러내자 전체 시간이 37% 줄었습니다.** 남은 병목은 커넥션 풀이며, 문지기는 결제 확정보다 앞단(주문·결제 준비)에 두는 것이 맞다는 결론입니다.

> ⚠️ 각 방식 **1회 측정값**입니다. 낙관적 락만 2회 측정해 재현성을 확인했습니다(충돌 1,296 / 1,291회, 성공 p50 1,292 / 1,285ms). 방식 간 차이가 큰 결론(초과 판매, 낙관적 락, Redis 문지기)은 1회로도 충분하지만, 비관적 락과 원자적 UPDATE의 9% 차이는 반복 측정으로 확정해야 합니다.

### 측정 방법
- **측정 대상**: `PaymentConfirmFacade.confirm()`을 직접 호출합니다. 주문 생성과 결제 준비는 측정 전에 순차로 만들어 둡니다.
- **방식 전환**: `stock.strategy` 설정값으로 `StockDecreaser` 구현체 하나만 빈으로 등록합니다(`@ConditionalOnProperty`).
- **정합성 지표**
  - 초과 판매 = 성공 건수 − 초기 재고
  - Lost Update = (초기 재고 − 최종 재고) ≠ 성공 건수
- **지연**: 요청별 시간을 성공과 품절로 나눠 p50/p95/max를 냅니다.
- **충돌 횟수**: Hibernate `Statistics.getOptimisticFailureCount()`
- **데이터 보호**: 테스트가 `local` 프로필을 쓰지 않고 접속 정보를 `shop_k6`로 직접 지정합니다. 1,000만 건 `shop` DB를 가리킬 여지를 없앴습니다.

```bash
./gradlew test --tests "*StockStrategyBenchTest" -PstockStrategy=atomic --rerun-tasks -i
# stockStrategy: naive | pessimistic | atomic | optimistic | redis-gate
```

## 1. 락 없음: 문제 재현

```java
Item item = itemRepository.findById(itemId);   // 락 없이 읽음
if (item.getQuantity() < quantity) return false;
item.removeStock(quantity);                     // 커밋 시 변경 감지로 UPDATE
```

```
[STOCK] success=300 outOfStock=0 finalStock=97 oversell=200 lostUpdate=true
```

**재고가 음수가 아니라 97이 된 이유**
변경 감지는 "현재 값에서 1을 빼라"가 아니라 **"내가 계산한 값으로 덮어써라"**라는 SQL을 만듭니다.
```
트랜잭션 A: SELECT → 100, 계산 99     트랜잭션 B: SELECT → 100, 계산 99
            UPDATE SET quantity = 99             UPDATE SET quantity = 99   ← A의 차감을 덮어씀
```
- **판매와 재고의 어긋남**: 300건이 거의 동시에 100을 읽고 각자 99를 썼습니다. 그래서 **300개가 팔렸는데 재고는 3개만 줄었습니다.**
- **검사 무력화**: `quantity < 1` 검사는 각자 읽은 오래된 값(100)으로 하니 전부 통과했습니다.
- **발견하기 어려운 이유**: 재고 값만 모니터링하면 이상이 보이지 않습니다.

**락이 없는데도 p50 995ms인 이유**: PostgreSQL은 같은 행을 수정하는 UPDATE끼리 행 락을 잡아 차례로 실행합니다. 다만 기다린 뒤 **다시 읽지 않고** 자기 계산값을 덮어써서 정합성은 깨졌습니다. 결국 "느리고 틀린" 상태였습니다.

## 2. 비관적 락 vs 원자적 UPDATE

```java
// 비관적 락
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select i from Item i where i.id = :id")
Optional<Item> findByIdForUpdate(Long id);       // SELECT ... FOR UPDATE

// 원자적 UPDATE (기존 방식)
UPDATE Item i SET i.quantity = i.quantity - :qty WHERE i.id = :id AND i.quantity >= :qty
```

| 방식 | 성공 p50 / max | 품절 p50 / max | 전체 |
|---|---|---|---|
| 비관적 락 | 573 / 958ms | 2,137 / 2,146ms | 2,161ms |
| 원자적 UPDATE | 596 / 989ms | 1,926 / 1,934ms | 1,968ms |

### 성공 경로: 차이 없음
두 방식 모두 완료 시점이 0~1초에 고르게 퍼져 있습니다. **한 행의 락을 건당 약 10ms씩 차례로 넘겨받는 구조**입니다. 인기 상품 하나의 결제 확정 처리량은 **초당 약 100건**이 상한입니다.

원자적 UPDATE도 락이 없는 방식이 아닙니다.
```
비관적 락:      SELECT ... FOR UPDATE (락) → Java 검사 → UPDATE → 결제·주문 변경 → COMMIT (해제)
원자적 UPDATE:                                  UPDATE (락) → 결제·주문 변경 → COMMIT (해제)
```
차이는 조회 왕복 한 번만큼 락을 짧게 잡는 것입니다. 재고 차감 뒤의 결제·주문 상태 변경이 커밋 때 flush되므로, 두 방식 모두 그 시간까지 락을 잡습니다.

### 품절 경로: 원자적 UPDATE가 약 210ms 빠름
| 방식 | 재고 0 이후 품절 요청의 동작 |
|---|---|
| 비관적 락 | `FOR UPDATE`로 여전히 락을 하나씩 잡고 0을 확인한 뒤 해제. 200건이 계속 줄을 섬 |
| 원자적 UPDATE | `WHERE quantity >= 1`에 맞는 행이 없어 **락 없이** 즉시 0건 반환 |

원자적 UPDATE를 고를 근거는 **"재고 부족 판정을 락 없이 끝낸다"**는 점입니다. 기존 포트폴리오에 적었던 "p95 79% 개선"은 같은 조건에서 재현되지 않았습니다.

### 품절 응답이 성공보다 2배 느린 이유
```
0ms ──────────────── 약 1,000ms ─────────────── 약 1,930ms
[성공 100건이 한 줄로 차감]  재고 0 도달
[품절 200건도 같은 락 대기열에서 기다림 …]  → 0 확인 → 롤백 → FAILED 기록 → 한꺼번에 끝
```
품절될 요청도 **자기 차례가 와서 UPDATE를 해 봐야** 재고가 없다는 것을 압니다. 그 뒤에도 롤백 → `markFailed`(새 트랜잭션) → Redis 실패 집계를 거칩니다. 늦게 온 200명은 **2초를 기다려 "품절"을 받습니다.**

## 3. 낙관적 락

```java
@Version private Long version;                     // Item

// 커밋 시: UPDATE item SET quantity=?, version=v+1 WHERE id=? AND version=v
// 0건이면 ObjectOptimisticLockingFailureException → Facade에서 재시도 (최대 30회, 무작위 대기 5~55ms)
```
충돌은 커밋 시점에 터지고 트랜잭션 전체가 롤백됩니다. 그래서 재시도는 **트랜잭션 밖(Facade)**에서 합니다.

| 회차 | 성공 p50 / max | 품절 p50 | 충돌 횟수 | error |
|---|---|---|---|---|
| 1 | 1,292 / 2,193ms | 3,100ms | 1,296 | – |
| 2 | 1,285 / 2,155ms | 3,024ms | 1,291 | 0 |

- **재시도 비용**: 충돌하면 재고 차감만이 아니라 **결제 조회, 권한 확인, 결제·주문 상태 변경까지 전부** 버리고 다시 합니다.
- **충돌이 예상보다 적은 이유**: 수천 건을 예상했지만 커넥션 풀(50)이 동시 경쟁자를 제한했습니다. 무작위 대기로 재시도가 분산됐고, 재고 0 이후에는 수정하지 않아 충돌도 없었습니다.
- **판단**: 낙관적 락은 판매자의 상품 정보 수정처럼 **충돌이 드문 곳**에 맞습니다.

**주의할 점**
- **JPQL 벌크 UPDATE는 버전을 올리지 않습니다.** 원자적 UPDATE 같은 쿼리와 섞으면 낙관적 락이 다른 수정을 감지하지 못합니다(`UPDATE VERSIONED`로 써야 함).
- **`@Version` 추가 시 기존 DB에 컬럼이 필요합니다.** `ddl-auto: none`인 1,000만 건 DB에는 `ALTER TABLE item ADD COLUMN version bigint NOT NULL DEFAULT 0`이 필요합니다.

## 4. Redis 문지기 + 원자적 UPDATE

```
요청 → Redis DECRBY stock:gate:{itemId}
        ├─ 결과 < 0 → INCRBY로 되돌리고 즉시 품절 (DB 락 대기열에 서지 않음)
        └─ 결과 ≥ 0 → DB 원자적 UPDATE (최종 정합성은 DB가 보장)
                        └─ 트랜잭션이 커밋되지 않으면 afterCompletion에서 Redis 차감 되돌림
```

```
[STOCK]       success=100 outOfStock=200 error=0 finalStock=0 oversell=0 total=1233ms
[STOCK-SPLIT] success{p50=699 p95=1205 max=1229} fail{p50=1006 p95=1094 max=1103}
[STOCK-GATE]  redis=0 db=0
```

| 설계 | 이유 |
|---|---|
| DB 원자적 UPDATE 유지 | Redis와 DB가 어긋나도 초과 판매는 불가능. 어긋남의 피해는 "덜 파는 것"에 그침 |
| `afterCompletion`에서 보상 | Redis 차감 후 DB가 롤백되면 Redis만 줄어 팔 수 있는 재고를 품절 처리하게 됨. 커밋 여부를 확인한 뒤 되돌림 |
| 키가 없으면 `SETNX`로 초기화 | 키 없이 `DECRBY`하면 0에서 시작해 전부 품절. 동시 초기화도 한 번만 설정 |

### 결과
- **품절 처리**: 품절 p50이 1,926 → 1,006ms로 48% 줄었습니다. 품절 요청이 DB 행 락 대기열에서 빠졌기 때문입니다.
- **전체 시간**: 1,968 → 1,233ms로 37% 줄었습니다.
- **정합성**: Redis 재고와 DB 재고가 모두 0으로 일치했습니다.

### 가설이 틀린 점: 품절 응답이 여전히 1초
Redis 판정은 1ms 미만인데 품절 응답은 1초였습니다. 문지기가 **결제 확정 트랜잭션 안**에 있기 때문입니다.
```
커넥션 대기 → 결제·주문 조회 → [Redis: 품절] → 롤백 → 커넥션 다시 대기 → FAILED 기록
```
요청 300건이 커넥션 50개를 나눠 쓰고, 품절 건은 커넥션을 두 번 얻습니다. 병목이 **행 락에서 커넥션 풀로 옮겨 갔습니다.** 성공 건 최댓값이 989 → 1,229ms로 늘어난 것도 같은 이유입니다. 이제 품절 건이 락 대기열이 아니라 커넥션을 놓고 성공 건과 경쟁합니다.

## 판단과 후속 과제

| 판단 | 근거 |
|---|---|
| 재고 차감은 원자적 UPDATE 유지 | 비관적 락과 성공 경로는 같고, 품절 판정을 락 없이 끝냄. 낙관적 락은 1.5배 느림 |
| 인기 상품 판매에는 Redis 문지기를 앞단에 둠 | 품절 요청을 DB 앞에서 걸러 전체 37% 단축. 정합성은 DB가 계속 보장 |
| 문지기 위치는 결제 확정이 아니라 주문·결제 준비 단계 | 확정 시점에 막으면 품절 사용자도 이미 주문·결제를 만들고 커넥션을 두 번 씀 |

### 후속 과제
- **반복 측정**: 방식별 3~5회 반복해 중앙값 확정 (특히 비관적 락과 원자적 UPDATE의 9% 차이)
- **재고 선점 설계**: 주문(또는 결제 준비) 시점 Redis 재고 선점 + 미결제 만료 시 반환
- **Redis 운영 과제**: 관리자 재고 수정·주문 취소 시 Redis 동기화, Redis 장애 시 DB 단독 처리, 재기동 시 키 복구(현재 영속화 없음)
- **Redisson 분산 락**: 비교군. 한 줄 세우기라 비관적 락과 비슷할 것으로 예상
- **같은 결제의 동시 중복 확정**: `READY` 확인에 락이 없어 재고 이중 차감 가능
- **다중 상품 주문의 데드락**: 비관적 락에서 상품 A, B를 반대 순서로 잠그는 경우. 상품 id 순 정렬로 해결 예정
- **HTTP 레벨 측정**: k6로 처리량과 p95 확인
